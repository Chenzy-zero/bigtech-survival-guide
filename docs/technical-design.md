# 技术方案与内容数据结构

## 1. 技术方向

建议采用轻量静态前端：
- Vite + 原生 TypeScript。
- 原生 HTML/CSS，不先引入 React/Vue 等 UI 框架。
- 剧情以 JSON 或 TypeScript 数据文件保存。
- 使用 Vitest 或同等轻量测试工具验证剧情数据与核心跳转。
- 第一版不需要后端；如需记住进度，可在后续版本使用 localStorage。

这是一项建议中的基线决策，开始实现前可根据原型需要调整。不要为了“现代化”而添加不必要的服务端、数据库或状态管理库。

## 2. 页面结构

- 首页：标题、反讽式简介、开始按钮。
- 游戏页：章节/进度、事件标题、情境文本、选项按钮。
- 反馈状态：显示选择带来的短期结果或荒诞反转。
- 结局页：结局标题、组织规则揭示、关键选择回顾、重新开始。

同一页面切换状态即可，不需要多页面路由。

## 3. 最小游戏状态

- currentEventId：当前事件 ID。
- decisions：本局的选择历史。
- flags：由选项设置的剧情标记。
- status：playing、won 或 lost。

第一版不强制使用复杂数值属性。通过剧情标记和事件跳转表达反转逻辑。

## 4. 事件数据结构

以下为建议的数据形状，不代表正式剧情：

~~~json
{
  "id": "probation-001",
  "chapter": "试用期",
  "title": "22:47，主管发来消息",
  "body": "明早上线的需求还没完成，主管要求今晚必须交付。",
  "choices": [
    {
      "id": "a",
      "text": "先确认交付范围、验收标准和测试时间",
      "feedback": "你把模糊要求变成了可讨论的范围。",
      "nextEventId": "probation-002",
      "setFlags": ["clarified_scope"]
    },
    {
      "id": "b",
      "text": "先在群里回复“收到，保证完成”",
      "feedback": "主管暂时满意，但你也亲手建立了一个不可能的预期。",
      "nextEventId": "ending-overpromise",
      "setFlags": ["promised_without_scope"]
    }
  ]
}
~~~

每个事件可以包含：
- id、chapter、title、body。
- choices：选项 id、显示文本、feedback、nextEventId 或 endingId。
- setFlags：选择后设置的剧情标记。
- clueTags：可用于记录反转线索或人物动机。
- sourceIds：引用 docs/research/sources.md 中的研究条目。

结局应有 outcome 与 explanation。失败说明要揭示触发陷阱的组织逻辑，而不是简单说玩家“做错了”。

## 5. 事件校验

- 事件 ID 全局唯一。
- 同一事件内选项 ID 唯一。
- 非结局事件有 2–4 个选项。
- 每个跳转目标都存在。
- 从开局事件可到达应当可玩的事件与结局。
- 不存在无入口的孤立结局。
- 重新开始会清空 decisions 与 flags。
- 关键反转事件有可识别的线索或前置剧情，不是纯随机作者杀。

## 6. 手机端要求

- 默认按 320–430 CSS 像素宽度设计，宽屏居中展示。
- 选项按钮整行可点击，触控目标建议至少约 44px 高。
- 正文字号舒适、行距清楚，避免长段落。
- 不依赖 hover 才能操作。
- 明确展示进度和当前章节，但不让状态面板挤占主要阅读区域。
- 支持键盘焦点、足够的颜色对比和语义化按钮。
- 减少不必要动画，尊重系统减少动态效果偏好。

## 7. 部署

首选 GitHub Pages 或其他静态托管。等原型可构建后再配置自动部署；不要在还没有应用代码时加入空转的 CI/CD 流程。
