# 技术方案与内容数据结构

## 1. 技术方向

建议采用轻量静态前端：
- Vite + 原生 TypeScript。
- 原生 HTML/CSS，不先引入 React/Vue 等 UI 框架。
- 剧情以 JSON 或 TypeScript 数据文件保存。
- 使用 Vitest 或同等轻量测试工具验证剧情数据与核心跳转。
- 第一版不需要后端；如需记住进度，可在后续版本使用 localStorage。

这是一项建议中的基线决策，开始实现前可根据首个原型的实际需要调整。不要为了“现代化”而添加不必要的服务端、数据库或状态管理库。

## 2. 页面结构

- 首页：标题、简短玩法介绍、开始游戏。
- 游戏页：章节/进度、事件标题、情境文本、选项按钮。
- 反馈状态：显示选择带来的简短结果，然后继续。
- 结局页：结局标题、原因说明、关键选择回顾、重新开始。

同一页面切换状态即可，不需要多页面路由。

## 3. 游戏状态

建议的最小状态：
- currentEventId：当前事件 ID。
- decisions：本局的选择历史。
- flags：由选项设置的剧情标记。
- status：playing、won 或 lost。

第一版不强制使用复杂数值属性。未来如确有需要，再加入 energy、managerTrust 等状态，并为每个状态明确取值范围和变化规则。

## 4. 事件数据示例

以下仅展示建议的数据形状，不代表正式剧情：

~~~json
{
  "id": "probation-001",
  "chapter": "试用期",
  "title": "22:47，主管发来消息",
  "body": "明早上线的需求还没完成，主管要求今晚必须交付。",
  "choices": [
    {
      "id": "a",
      "text": "先确认必须交付的范围、验收标准和风险",
      "feedback": "你把模糊要求变成了可讨论的范围。",
      "nextEventId": "probation-002",
      "setFlags": ["clarified_scope"]
    },
    {
      "id": "b",
      "text": "不问细节，直接承诺全部完成",
      "feedback": "承诺先于评估，风险开始累积。",
      "nextEventId": "ending-overpromise"
    }
  ]
}
~~~

建议约束：
- id 全局唯一。
- 每个非结局事件有 2–4 个 choices。
- 每个 nextEventId 都必须指向存在的事件。
- 结局事件标记为 ending，并有 outcome 与 explanation。
- 每个选项可以设置反馈、标记和目标事件。
- 来源信息可以放在事件的 sourceIds 字段，并引用 docs/research/sources.md 中的条目 ID。

## 5. 校验与测试

开始实现事件引擎后，至少校验：
- 重复事件 ID。
- 重复选项 ID（同一事件内）。
- 不存在的跳转目标。
- 非结局事件没有选项或选项数量超出约定。
- 无法从开局事件到达的事件。
- 没有任何入口路径可以到达的结局。
- 重新开始时本局 decisions 和 flags 已清空。

## 6. 手机端要求

- 默认按 320–430 CSS 像素宽度设计，宽屏居中展示。
- 选项按钮尽量整行可点击，触控目标建议至少约 44px 高。
- 正文字号舒适、行距清楚，避免长段落。
- 不依赖 hover 才能操作。
- 明确展示进度与当前章节，但不要让状态面板挤占主要阅读区域。
- 支持键盘焦点、足够的颜色对比和语义化按钮。
- 减少不必要动画，尊重系统减少动态效果偏好。

## 7. 部署

首选 GitHub Pages 或其他静态托管。等原型可构建后再配置自动部署；不要在还没有应用代码时加入空转的 CI/CD 流程。
