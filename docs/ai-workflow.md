# AI 辅助开发工作流

本项目可以使用 Codex、Claude Code、GitHub Copilot 或 Cursor 协作。根目录 AGENTS.md 是通用规则的唯一事实来源，各工具专属文件只做入口说明。

## 0. Issue-first：先找到任务，再动手

所有需求、开发任务和 Bug 都必须通过 GitHub Issue 管理。开始工作前先搜索现有 Issues；如果没有对应 Issue，先创建一个。Issue 必须引用真实的仓库文档或代码路径，并包含目标、范围和验收标准。

建议提示词：

~~~text
开始前请先检查 GitHub Issues，找到与当前任务对应的 Issue；若不存在，请先创建。
阅读 Issue 引用的仓库文档和 AGENTS.md，再检查当前实现。
请先说明目标、涉及文件、最小方案、风险和验收方法，不要立即修改无关文件。
~~~

## 1. 先规划

适用于新增页面、调整事件模型、扩展剧情引擎等中型任务。计划应与 Issue 的范围和验收标准一致；若发现需求变化，应先更新 Issue。

## 2. 小步实现

~~~text
按已确认的 Issue 和计划实现最小变更。保持剧情数据与 UI/引擎分离。
不要顺带重构无关代码。完成后运行适用的测试和构建，并检查 diff。
~~~

## 3. 自我审查

~~~text
请像代码审查者一样检查本次 diff：寻找错误的剧情跳转、无法到达的结局、重开后残留状态、手机端可用性问题和无必要的复杂度。
同时检查反转是否有铺垫、是否把所有认真选择都机械地设成失败，以及是否把拍马屁/摸鱼写成了每题固定答案。
先报告问题，再修复确实存在的问题，最后重新运行验证。
~~~

## 4. 编写或修改剧情

~~~text
请为指定章节设计职场事件。每个事件包含唯一 ID、背景、2–4 个选项、结果反馈和有效跳转。
采用荒诞职场讽刺：看似正确的选择可能在下一步变成坑，溜须拍马或摸鱼可能暂时奏效，但反转应有线索并符合虚构组织的扭曲激励机制。
不要写成严肃职场教学，也不要让每题都变成毫无提示的随机惩罚。
如使用真实资料，请引用 docs/research/sources.md 中的来源 ID，并区分事实与虚构改编。
~~~

## 给 AI 的任务上下文

每次任务尽量明确 Issue 编号、用户体验目标、不在本次范围内的内容、相关文件、验收标准和需要运行的验证。PR 必须关联 Issue。

## 防止 AI 过度开发

- 不因“未来可能需要”就提前增加后端、数据库、插件系统或通用框架。
- 不把简单选择游戏扩展成大型 RPG。
- 不生成没有来源标注的“真实案例”。
- 不在未运行测试时声称测试通过。
- 任何新增依赖都应说明为何现有原生能力不足。
