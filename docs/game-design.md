# 游戏设计与核心规则

## 1. 核心体验：一题不对，当场出局

《大厂生存指南》是荒诞职场选择游戏，不是职场培训，也不是让玩家攒线索解谜。玩家扮演刚毕业的求职者/新人，在简历、面试、谈薪、Offer、入职、团建、日常汇报和事故处理等生活化场景中做选择。

核心节奏是“看到一件小事 → 选一句话/做一个动作 → 立刻看到后果”。有些选择会进入下一场景，有些会马上收到“面试未通过”“岗位取消，暂不录用”或“试用期流程终止”的通知。失败不需要等到最后统一结算。

## 2. 场景写作规范

每个非结局事件必须做到：

- 标题像日常里会发生的一刻，例如“HR 问你的期望薪资”“周五 17:50，主管发来团建通知”。
- 正文通常 1–3 句话，交代人物、当前事情和玩家面临的直接问题。
- 使用生活化中文，少用抽象的管理口号。避免把“组织激励、隐藏规则、线索”等解释直接写进题干。
- 不展示独立的“线索”提示卡。玩家从对话、邮件、群消息和具体后果中理解荒诞之处。
- 选项应当是具体说法或行动，而不是“选择 A 路线”“提升协同效率”等抽象标签。
- 选项反馈尽量短。若失败，直接说发生了什么；若继续，交代下一步。
- 不为追求反转而故意写模糊题干。场景要清楚，荒诞来自组织反应，不来自玩家看不懂题目。

## 3. 快速失败规则

每个主要阶段都应至少有一个即时失败分支：

1. 简历：夸大项目职责，面试追问穿帮；或只写空话，简历筛选未通过。
2. 项目面试：讲不清个人贡献，或把团队成果说成个人成果，面试结束。
3. 项目数据：编造指标，被追问统计口径后淘汰。
4. 薪资沟通：不确认固定薪资/绩效结构，或开出远超岗位范围的最后通牒，流程终止。
5. 口头 Offer：未拿到书面 Offer 就辞职，收到“岗位因业务调整取消，暂不录用”。
6. 书面 Offer：只看总包不看条款，入职后发现奖金和岗位与预期不同。
7. 入职与团建：文化仪式、隐性融入评价或可被证伪的借口触发独立结局。
8. 日常汇报：只说空话或冒领同事成果，工作被转走/试用期结束。
9. 紧急任务：无条件承诺、用 PPT 代替交付，直接进入过劳或交付失败结局。
10. 线上事故与复盘：无证据甩锅、不更新状态、把系统问题全揽成个人问题，都可立即出局。

失败结局必须独立命名，不用一个通用“你被优化了”覆盖所有情况。结局页要写清楚：发生了什么、玩家为什么在这一刻出局，并允许重新开始。

## 4. 结局设计

- **求职阶段**：简历筛选失败、项目追问穿帮、数据造假、薪资预期错位。
- **Offer 阶段**：口头 Offer 后先辞职导致岗位取消、提前摊牌导致两边都没准话、签约后发现条款落差。
- **入职阶段**：文化融入评价、团建隐性考核。
- **工作阶段**：空话汇报、冒领成果、PPT 绿灯但实际无法交付、事故甩锅、事故沟通失联。
- **复盘阶段**：只会自我检讨、用黑话代替整改。
- **暂时存活**：说清事实、未知项、负责人和验证时间。这不是“正确人生答案”，只是这一次没有被荒诞机制吞掉。


## 4.1 新路线：夸主管、战略摸鱼与反噬（Issue #15）

由早会 `standup-009` 的新选项进入 `praise-013`、`busy-014`、`showcase-015`。这条路径不是教玩家投机，也不是全程口号式选择题，而是让玩家经历组织奖励方向与真实交付之间的错位。

1. 早会先夸主管“选题有眼光”，主管马上把下午的汇报任务交给玩家。一次表演带来新工作，而不是直接奖励。
2. 玩家做汇报时保留“未完成”的事实与负责人，主管却首先表扬 PPT 好看；反过来，只讲故障不做汇报可能被认为“不懂向上管理”，造假宣称“已上线”则当场翻车。
3. 玩家用两项明确待办交代进度，其余时间在楼下喝咖啡。组织看见消息密度，错误以为新人很忙。直接失联或无限揽活则触发不同的失败。
4. 老板突然要求演示，玩家必须拿出此前记录的未完成项并请负责开发的同事说明进度，才能进入荒诞存活结局。空口甩锅与主动全揽风险，会马上失败。

**新暂时存活结局：**“你没修 Bug，却被夸成了项目推进能手”。主管指定你以后专门负责每周汇报；短期得利成了新的长期负担。存活不是道德评价。

该路线用现有 `setFlags` / `requiresFlags` 体现前后选择因果，不新增独立线索卡，不暴露隐藏概率与数值。与原“清晰汇报→事故复盘”路线并存，且互不覆盖。

## 5. 大厂黑话与现实素材

黑话以公开媒体报道和受访者经历为素材，但要区分年代、语境和证据：

- 跨公司常见表达：对齐、拉通、颗粒度、抓手、赋能、闭环、链路、沉淀、打法、落地、复盘、资源倾斜、业务价值、投入产出。
- 可以出现英文混用：owner、landing、to do、re 一遍等，但必须符合具体人物与场景，不能每道题都塞满术语。
- “阿里味”、花名、325/375 等应标作特定历史语境里的企业文化/绩效梗，不要写成所有阿里团队当下的统一规则。
- 字节相关吐槽可以围绕 OKR、周报/复盘、职责边界、业务变化、飞书消息和高强度工作展开；这些是媒体采访中的个体经历，不等于所有部门都如此。制度会随时间变化，不能把旧的双月 OKR 当作当前固定制度。
- 不把“主人翁精神”作为当下核心黑话或通用梗。公开资料中出现过它，只能作为特定历史语境的用语，不代表它是当前高频表达。

讽刺对象是术语堆砌、空泛汇报、模糊责任和口头价值观与实际激励的错位，不是把所有专业词汇或所有大厂员工一概否定。

## 6. 事件与引擎约定

- 每个事件有唯一 ID、章节、标题、简短情境、2–4 个选项。
- 每个选项都跳转到一个存在的事件或结局。
- 结局使用数据结构标明 won/lost，包含标题、结果描述和简短解释。
- 允许剧情标记作为后续扩展，但当前 MVP 不需要复杂属性系统。
- 事件图校验所有节点可达、选项 ID 唯一、跳转目标存在；测试覆盖各阶段的代表性即时失败分支。
- 重新开始会清空选择记录和剧情状态。

## 7. 内容边界

真实报道只作为创作参考。剧情使用虚构公司与复合场景，不把个体吐槽写成特定企业的普遍事实。薪资、Offer、团建等情节不构成现实中的法律或职业建议。过劳和健康风险作为警示呈现，不当作轻松笑料。
